# 原生工程与共享几何

用户要求H盘仅保留代码。因此完整资产继续在F盘，代码副本不能代替模型备份；不批量更改Blender/MCP的工程根目录。

020r2在核对已有图片编码字节后外置了重复打包图像，完整原生仍为895,350,029字节。只读盘点显示主要剩余体积来自既有树木枝叶与摄影网格，逐次完整复制会持续耗尽工作盘。020r3采用同一场景、同一几何和材质的存储变体：对象、集合、相机、材质及树干仍在新文件中本地可编辑；2,169个不改动的重型网格由保留的020r2检查点提供。

**必须同时保留：**

- `native/G1_020r3_linked_working.blend`及后续基于它的工作文件。
- `native/G1_020r2_utoquai_coating_working.blend`，是明确的永久几何依赖，不能覆盖、移走或清理。
- `sources`与`derived/materials`等原项目图像和数据依赖；两份`.blend`单独放在别处也不等于完整工程。

共享工程使用`//G1_020r2_utoquai_coating_working.blend`相对引用，不形成逐版串联的依赖链。对象保留原身份、父子关系、位置、可见性及集合；材质改为对象级引用本地原材质，因此后续材质编辑仍独立可用。引用网格如需改形或改UV，先为该对象作`obj.data = obj.data.copy()`，再修改本地副本；不能直接写只读库网格。之后替换摄影节点时也给对象赋新本地网格，原始参考仍保留。

转换程序`blender_share_static_geometry.py`必须在新的空白Blender进程中运行。它先从020r2追加完整场景，再将明确选定的网格改为同文件的链接几何，逐项比对坐标、拓扑、材质面索引、UV、颜色和其它数值属性。它不删源数据、不减少几何、不降低图像分辨率，也不把存储改进称为视觉改进。

第一轮因Blender将传入列表原位改写为ID对象而退出1，没有保存候选；已改成传入独立列表。第二轮转换成功保存155,754,863字节的020r3，源020r2保留。独立进程重开已通过2,169个网格的完整数值指纹、9,325个对象状态及图像依赖核验，南向同机位实图已查看。画面保留原几何、物体、阴影和未修摄影问题；与020r2图的8位像素平均绝对差为0.051，最大差9，不宣称逐像素相同。工作指针已更新到020r3，实时默认仍为007r5，候选仍为018r3。

检查期间修正了渲染脚本的材质查找：共享网格的实际材质来自对象级覆盖，不能继续只读取`obj.data.materials`。第一次图和日志保留；修正后重新独立渲染并实际查看，原作者贴图与全部几何不降级。后续导出、烘焙与检查同样应读取实际材质槽；不能把新格式存储成功直接当作这些环节已经通过。

存储收据在`evidence/G1_020r3/shared_geometry.json`。这是继续施工的容量维护，不缩小G1范围，也不代表原生、导出和实际使用已一致验收。

020r4随后把8张仍指向临时目录的内嵌沥青/木皮图保存到永久的`sources/textures/polyhaven/asphalt_03`和`oak_veneer_01`目录。编码字节逐一SHA256相同，分辨率、色彩空间和alpha状态相同；没有重压缩图片或改变它们的内容。新工作文件降为63,388,164字节，原8张图片共92,992,245字节单独保留，此后不必每版重复内嵌。旧文件都保留，因此这是减少后续新增占用，不能称为本轮直接腾空同样体积。
